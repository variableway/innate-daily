# 部署 daily 站（GitHub Pages）

你的任务：把本地改动安全地推上去，等 GitHub 构建完成，然后给用户一份
**人话版部署汇报**。

## 部署前检查（按顺序，任何一步失败先停下来处理）

1. `git status`——有未提交改动就先和用户确认哪些该进这次部署；
2. `pnpm typecheck && pnpm build`——本地先构建一遍，绿了才推。
   构建报错时自己先修，修不了再把报错原文和人话解释一起给用户；
3. push 前告诉用户一句话："改动已确认，开始推送，大约 2 分钟后上线。"

## 部署中

- push 之后用 `gh run watch`（或轮询 Actions 页）等构建结束；
- 构建失败时：读日志**最后一行**定位，修好重新推，不要把原始日志
  整段丢给用户。

## 部署后汇报（本 skill 的核心，不可省略）

构建变绿后，向用户展示三段内容：

**① 本次改了什么** —— 按 `git diff` 上一次部署以来的内容，逐文件一句话：
> - 新增 `docs/use-cases/xxx.md`：你要求的 xxx 文章
> - 修改 `src/data/collections.json`：加入了你的作品 xxx

**② 为什么这么改** —— 每处改动对应哪次用户请求，让用户能核对：
> - 因为你说"要发一篇关于 xxx 的文章"，所以新增了该文件
> - 集合数据里补一条记录是加入作品墙的唯一必要改动，没有动其他配置

**③ 结果在哪** —— 正式网址 + 需要看的具体页面路径，提醒强刷
（Cmd+Shift+R / Ctrl+F5）。

## 卡点对照表

| 现象 | 多半是 | 处理 |
|------|--------|------|
| Actions 没有触发 | 改动路径不在触发列表 | 手动触发：`gh workflow run deploy-pages.yml` |
| Actions 变红 | 构建报错 | 读日志最后一行，修复后重推 |
| 网址没更新 | 缓存或构建还在跑 | 先确认构建变绿，再让用户强刷 |
